За 323 с наблюдения: **воркер 26300 отдавал новое меню, остальные три воркера (26299, 26301, 26306) — старое на каждой проверке, ни разу «смешанно»**, т.е. 3 из 4 воркеров (75%) стабильно отдают старое меню; пользователь видит новую категорию с вероятностью 1/4 на запрос (пока не истечёт кэш воркера).
- Сколько длится: ключевая оценка — до TTL фрагмента `{% cache 3600 ... %}` в `base.html:27,87`, т.е. до 3600 с с момента заполнения кэша КАЖДЫМ воркером; наблюдение было 323 с (час не ждали), верхняя граница 3600 с — из кода, а не измерена. Кэш по языкам (ключ с `current_language`) — каждый язык инвалидируется отдельным ключом только в том же процессе. После рестарта/нового деплоя кэш пуст (холодный старт выше). На нескольких dyno стало бы то же самое.
- Замечание по методике: round-robin ядра ОС распределяет запросы неравномерно (в отдельных раундах по 60 запросов виден не каждый воркер), поэтому «сколько воркеров» посчитано как объединение pid по всем раундам.

## D6. Оценка для хостинга (Heroku): оценка, не измерение

Измерено: число запросов к БД на страницу (прогретый кэш): `/` 4, статья 7 (включает `UPDATE views` на КАЖДЫЙ просмотр, в т.ч. HEAD), категория 2, поиск 1, `/all` 1, sitemap 6, feed 1, `/authors` 1. Для миксa 35/35/15/10/5 это ≈4.3 запроса/запрос. «Лёгкий» микс: ≈38 RPS на воркер ⇒ ≈160–210 SQL/с на воркер при 4–7 запросах на страницу (локально).

Допущения (из моих знаний о Heroku, без обращения к сайту — не проверено): router timeout 30 с (H12); Eco/Basic/Standard-1X — 512 МБ RAM, 2X — 1 ГБ (R14 при превышении); CPU разделяемый и медленнее моего Apple Silicon (допущу 2–4× по времени); MySQL — аддон (JawsDB/ClearDB) с малым лимитом соединений и сетевой задержкой до БД; `CONN_MAX_AGE=600` ⇒ 1 соединение на воркер, процесс `web` по Procfile — **1 sync-воркер** (нет `-w`).

Что это даёт:
- Ёмкость: ≈4 запросов/с для текущего миксa (с `/all`, поиском, категориями) на 1 воркер, ≈38/с для «главная+статья». Один посетитель, открывший `/all`, занимает воркер на ≈1.4 с (локально; на dyno 3–6 с по допущению 2–4×); при одном sync-воркере все остальные ждут. Из таблицы: линейная модель 0.21 мс/статью ⇒ 30-секундный router timeout при ≈140 тыс. опубликованных ua-статей локально или ≈35–70 тыс. на медленном dyno (экстраполяция).
- Память: один запрос `/sitemap.xml` или `/all` поднимает процесс до 350–414 МБ (maxrss на macOS) ⇒ на 512 МБ dyno с 1 воркером риск R14, с 2+ воркерами почти наверняка (2 воркера × 300–400 МБ). Статья с 5 000 комментариев — 280 МБ и 9.4 МБ HTML (на мобильной сети ≫ секунды).
- Запросы к БД: сетевая задержка добавляется к КАЖДОМУ из 4–7 запросов страницы: при RTT 5/20 мс (допущение) +20–35 / +80–140 мс на страницу; поиск — полный скан 94 МБ на каждый запрос даже без совпадений (133 мс локально).
